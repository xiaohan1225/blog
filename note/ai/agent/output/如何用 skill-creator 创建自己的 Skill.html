如何用 skill-creator 创建自己的 Skill ​

这是 Skill 系列的第三篇。本文重点不是手写一个 SKILL.md，而是讲如何让 Codex 使用 skill-creator 自动创建或更新 Skill。

先说结论 ​

创建 Skill 最省事的方式，不是自己手写目录，也不是自己去找初始化命令，而是直接让 Codex 使用 skill-creator。

你要做的是把需求说清楚：

  • Skill 名称或大致用途。
  • 什么时候触发。
  • 需要完成哪些任务。
  • 期望输出什么。
  • 是否需要脚本、参考资料或模板。
  • 安装到哪里，比如全局 ~/.codex/skills，还是当前项目目录。

skill-creator 会负责把这些信息整理成一个可复用的 Skill。

什么时候应该创建自己的 Skill？ ​

如果一个任务只做一次，不一定要写 Skill。

但如果你发现自己反复对 AI 说同样的话，就应该考虑沉淀成 Skill。

典型信号包括：

  • 你经常复制同一段 prompt。
  • 你经常纠正 AI 的同一种错误。
  • 你希望某类输出保持固定格式。
  • 你有一套自己的审美、流程或判断标准。
  • 你希望换工具后仍能复用这套经验。

比如写文章这件事，如果你每次都要提醒：

text
不要写得太像 AI。
开头别废话。
先给结论。
每段短一点。
保留关键判断。
不要乱用形容词。

那就应该做一个写作 Skill。

如何给 skill-creator 下任务？ ​

最简单的说法是：

text
使用 skill-creator，帮我创建一个 weekly-report skill。
它用于把零散工作记录整理成周报，需要包含信息归类、风险提炼、下周计划和输出格式。
放到全局 Codex skills 目录。

如果任务更复杂，可以把目标、触发条件、能力、资源和位置写清楚：

text
使用 skill-creator 创建一个 contract-review skill。

目标：
当用户要求审阅合同、识别风险条款、总结修改建议时触发。

能力：
1. 提取合同主体、金额、期限、付款和违约责任。
2. 标记高风险条款和模糊表述。
3. 给出修改建议和需要人工确认的问题。
4. 输出一份结构化审阅摘要。

资源：
需要 references/clause-checklist.md 记录常见条款检查清单。
需要 assets/ 存放审阅报告模板。

位置：
安装到全局 Codex skills 目录。

这类请求比“帮我创建一个合同 Skill”稳定得多，因为它给了 skill-creator 足够的边界。

skill-creator 会做什么？ ​

skill-creator 不是只生成一个空文件夹。它会把创建 Skill 拆成一套流程：

  1. 理解这个 Skill 要解决什么问题。
  2. 追问或整理几个真实触发例子。
  3. 规划是否需要 scripts/、references/、assets/。
  4. 创建 Skill 目录和 SKILL.md。
  5. 写好 name、description 和正文流程。
  6. 必要时补充资源文件。
  7. 校验 Skill 结构和触发描述。
  8. 根据真实任务继续迭代。

这种方式的好处是，skill-creator 会站在“另一个 Codex 将来怎么使用这个 Skill”的角度来设计，而不是只帮你写一份说明文档。

底层可能仍然会创建目录、生成 SKILL.md、补充资源文件、做校验，但这些是执行细节，不需要用户自己手动操作。

第 1 步：用具体例子定义 Skill ​

不要一开始就写一个“大而全的万能 Skill”。

适合做成 Skill 的任务，通常有几个特点：

  • 你经常做。
  • 你已经形成了一套判断标准。
  • 每次做都需要类似流程。
  • 任务结果可以被检查。

比如：

  • 写工作周报。
  • 审阅合同。
  • 整理会议纪要。
  • 审校文章。
  • 生成产品需求文档。
  • 把 Mermaid 图转换成图片。

更好的做法，是先列出 3 到 5 个真实使用例子。

比如你要创建一个“合同审阅 Skill”，可以先写：

text
用户说：帮我看一下这份合同有没有明显风险。
用户说：把这份采购合同里的付款、验收和违约条款整理出来。
用户说：给我一份合同审阅摘要，并列出需要法务确认的问题。

然后分析这些例子：

  • 用户通常会提供什么输入？合同文本、合同类型、关注重点。
  • AI 应该产出什么？风险摘要、条款清单、修改建议、待确认问题。
  • 哪些规则是稳定的？先提取关键条款，再判断风险，最后给修改建议。
  • 哪些资源可以复用？条款检查清单、审阅报告模板、常见风险说明。

这一步的目标，是把 Skill 的边界从“我想要一个合同 Skill”变成“这个 Skill 负责哪些输入、流程和输出”。

第 2 步：给 Skill 正确命名 ​

Skill 名称不是随便起的。

建议遵守这些规则：

  • 只使用小写字母、数字和连字符。
  • 文件夹名和 Skill name 保持一致。
  • 控制在 64 个字符以内。
  • 尽量短，但要说明动作。
  • 需要时用工具或平台做命名空间。

比如：

text
weekly-report
contract-review
markdown-mermaid-to-images
gh-address-comments
linear-address-issue

不建议这样命名：

text
My Awesome Skill
super-ai-helper
do-everything
写文章神器

命名越具体，越不容易和其他 Skill 冲突。

第 3 步：写好 description ​

description 不是给人看的简介，而是给 AI 用来判断“什么时候该加载”的触发条件。

一个好的 description 应该包含三类信息：

  • 能力：这个 Skill 能做什么。
  • 场景：什么时候使用。
  • 触发词：用户说哪些话时应该想到它。

示例：

yaml
---
name: contract-review
description: "审阅合同并提取风险。适用于合同审阅、条款检查、风险识别、修改建议。当用户要求检查合同、总结合同风险或整理关键条款时使用。"
---

不要只写：

yaml
description: "处理合同"

因为处理合同的场景太多了：审阅、翻译、摘要、归档、比对版本都可能匹配。边界太宽，冲突就会变多。

还有一个容易忽略的点：什么时候使用，最好写在 description 里，而不是只写在正文里。

原因很简单：AI 只有在 Skill 触发后才会读取正文。如果触发条件只写在正文里，模型可能根本不会加载这个 Skill。

第 4 步：规划资源目录 ​

Skill 不一定只有说明文字。它可以包含：

  • scripts/：重复、脆弱、需要稳定执行的脚本。
  • references/：长文档、规范、API、业务知识。
  • assets/：模板、图片、字体、示例项目、PPT 模板。
  • agents/openai.yaml：面向 UI 展示的名称、简介和默认提示。

判断方法很简单：看真实例子里有哪些事情会反复出现。

如果每次都要重写同一段代码，就放进 scripts/。

text
pdf-editor/
├── SKILL.md
└── scripts/
    └── rotate_pdf.py

如果每次都要查同一套表结构、接口文档或公司规范，就放进 references/。

text
bigquery-analytics/
├── SKILL.md
└── references/
    ├── finance.md
    ├── sales.md
    └── product.md

如果每次都要用同一套模板或素材，就放进 assets/。

text
frontend-webapp-builder/
├── SKILL.md
└── assets/
    └── starter-template/

很多低质量 Skill 的问题，是把所有东西都塞进 SKILL.md，最后文件臃肿、加载成本高、重点不清楚。

第 5 步：把流程写成可执行步骤 ​

Skill 不是理念宣言，而是操作手册。

不要只写：

markdown
你要写得专业、自然、有深度。

这类要求太抽象，模型知道方向，但不知道怎么落地。

更好的写法是：

markdown
## 工作流程

1. 先判断文章类型：教程、解释型文章、架构文章、对比文章或复盘文章。
2. 根据文章类型选择对应结构。
3. 开头先给 TL;DR，不要写泛泛背景。
4. 每个关键判断必须解释原因。
5. 涉及代码时，代码块必须标注语言，并保证示例可以独立理解。
6. 结尾写清楚适用场景和限制。

写流程时，还要控制自由度。

自由度适合场景写法
高自由度写作、方案、设计评审规则、原则、判断标准
中自由度有固定模式但允许变化伪代码、流程图、参数化步骤
低自由度容易出错、必须稳定执行脚本、固定命令、少量参数

比如“写分析文章”可以保留较高自由度，因为不同主题需要不同表达。

但“把 Mermaid 图渲染成图片”就应该降低自由度，最好提供脚本和固定命令，而不是让 AI 每次自己想办法。

第 6 步：写质量标准和反例 ​

好的 Skill 不只告诉 AI “应该做什么”，还要告诉它“不要做什么”。

比如文章整理 Skill 里可以写：

markdown
## 避免

- 不要使用“在当今快速发展的时代”这类空泛开头。
- 不要把核心结论埋在三段背景之后。
- 不要写无法运行的代码片段。
- 不要假装方案没有取舍。
- 不要使用营销话术替代具体解释。

反例很有用。它能把“我不喜欢这种感觉”翻译成模型可以执行的约束。

第 7 步：按渐进加载拆分内容 ​

当 Skill 变大以后，不要继续往 SKILL.md 里塞内容。

渐进加载的核心原则是：

  1. 元信息始终短小，用来触发。
  2. SKILL.md 只放核心流程，最好不要超过几百行。
  3. 长资料放到 references/，并在 SKILL.md 里说明什么时候读取。
  4. 可重复执行的操作放到 scripts/，不要让 AI 每次重写。
  5. 最终产物需要的模板和素材放到 assets/。

例如：

markdown
## 高级功能

- 处理表单字段：读取 `references/forms.md`
- 处理修订痕迹：读取 `references/redlining.md`
- 需要批量转换：运行 `scripts/convert_batch.py`

这样 AI 不需要每次加载所有资料，只在任务需要时读取对应文件。

第 8 步：让 skill-creator 验证 Skill ​

Skill 写完后，不要只靠感觉判断。

你可以继续让 Codex 使用 skill-creator 做验证：

text
使用 skill-creator 检查这个 skill 是否合格：
/Users/xxx/.codex/skills/contract-review

重点检查：
1. description 是否能准确触发。
2. SKILL.md 是否太长。
3. scripts、references、assets 是否拆分合理。
4. 是否存在和其他 skill 冲突的地方。
5. 是否缺少真实使用例子。

skill-creator 会从几个角度检查：

  • SKILL.md 是否存在。
  • YAML FrontMatter 是否合法。
  • name 和 description 是否存在。
  • Skill 名称是否符合规则。
  • 目录结构是否有明显问题。
  • SKILL.md 是否把太多内容塞进正文。
  • 资源目录是否真正有必要。
  • 触发边界是否清楚。

如果 Skill 里包含脚本，还应该实际运行脚本，确认它能工作。脚本类 Skill 最怕“看起来写了工具，实际跑不通”。

创建 Skill 时最容易犯的错误 ​

1. 把 Skill 写成大号 System Prompt ​

System Prompt 是全局规则，适合放长期不变、每次都要遵守的要求。

Skill 是按需加载的模块，适合放某类任务的专业流程。

如果你把所有规则都塞进一个 Skill，最后它就会变成另一个臃肿的 System Prompt。

2. description 太宽泛 ​

触发描述越模糊，越容易误触发。

比如：

yaml
description: "帮助用户写东西"

这会匹配文章、邮件、代码注释、产品文档、广告文案、小说，几乎没有边界。

更好的方式是拆成多个 Skill：

  • 周报整理。
  • 商业文案写作。
  • 产品需求文档。
  • 审校润色。

每个 Skill 只解决一个稳定场景。

3. 只写原则，不写流程 ​

“专业”“自然”“高质量”“深入”都不是可执行步骤。

Skill 里需要把这些词翻译成动作：

  • 开头先给结论。
  • 每个判断解释原因。
  • 涉及工具时给出命令。
  • 涉及代码时说明运行方式。
  • 最后写限制和下一步。

4. 放太多无关文档 ​

Skill 不是给人看的项目文档仓库，而是给 AI 执行任务用的工作包。

通常不需要额外创建：

  • README.md
  • INSTALLATION_GUIDE.md
  • QUICK_REFERENCE.md
  • CHANGELOG.md

除非某个文件会被 AI 在执行任务时直接使用，否则不要放进 Skill。

结论 ​

用 skill-creator 创建 Skill 的重点，不是让 AI 帮你写一个更长的 prompt，而是让它把一类高频任务整理成可触发、可执行、可维护的工作流。

你提供越具体的使用例子、触发条件、输出要求和资源需求，skill-creator 生成的 Skill 就越稳定。

一个好 Skill 的第一版不需要完美。先让它在真实任务里跑起来，再根据失败点补规则、补反例、拆资源、加脚本，这才是 Skill 真正变强的过程。
